# 科研推进工作流（从 rdbp_face 项目提炼，2026-07-03）

适用场景：已有工程基础和初步实验、但还没有科研级推进的项目——相关工作没摸清、novelty 未定、评估协议朴素、投稿无规划。本工作流在 rdbp_face（人脸识别双分支）上完整验证：一天内完成 4 项调研（70+ 组对抗检索、~60 篇论文入表）、novelty 判词定稿、评估协议升级、投稿规划成形。

## 0. 角色分工

- **规划 agent（director）**：项目分析、出调研任务书、验收产出、整合沉淀、联动实验计划。**不亲自做全量调研**（允许少量 scoping 检索），token 花在判断而不是搜索上。
- **内容 agent（每任务一个新会话）**：按任务书执行文献调研，写报告文件，在对话里给 ≤10 行执行总结。
- **用户**：路由器与决策者——把任务书转发给内容 agent、把执行总结粘贴回规划 agent、对方向性选择拍板。
- **教学 agent（可选但推荐）**：当调研速度超过用户理解速度时，专职把概念教懂用户——最终对外讲故事的是用户本人，不是 agent。

## 1. 前置：项目文档骨架

新项目先建立（轻量即可，一次性成本）：

```text
README.md               当前状态、关键路径、下一步（常更新，新会话的入口）
<migration/dev>_notes.md 实现细节、设计决策、风险、下一步计划
concept_notes.md        方法理解（教学与"论文语言"描述的底本）
<experiment_report>.md  实验记录：结论先行、关键配置、关键数字、限制、阶段结论
research/               调研任务书 + 报告 + 汇总页（本工作流的主战场）
CLAUDE.md               工程 agent 的角色与上下文加载规则
```

两条贯穿性实验纪律（写进 CLAUDE.md）：

1. **训练健康指标 ≠ 最终收益指标**——loss 下降只说明链路通，收益必须看验证集；记录里必须区分。
2. **每次实验只改一个主要因素**，保证结果可归因。

## 2. Phase 0：项目分析（T0，规划 agent 亲自做）

产出 `research/T0_project_analysis.md`，四件事：

1. **方法的"论文语言"描述**：剥离工程名词（数据格式、脚本名、路径），写成能与文献直接对比的机制描述——结构（什么冻结、什么可训、从哪分叉）、信号（什么信息、在线还是离线、可解释性）、约束（loss 的数学形式、作用对象、方向）。这一步决定后面所有检索问得对不对，是全流程最重要的一步。
2. **证据分级**：已证明（带数字）/ 未证明 / 进行中。诚实分级；短训 smoke 不当最终收益。
3. **novelty 候选轴 2–3 个**：每轴一句可被文献检验的主张，作为后续调研的靶子（预期大部分会被文献部分击破——这是流程的正常运作，不是失败）。
4. **与用户确认理解无误后**，再设计任务书。

## 3. Phase 1：调研任务序列（T1–T4 模板）

**串行执行**：前序任务确认的锚点（必比先例、更正、可复用检索词）注入后续任务书，避免重复劳动、保证口径一致。

- **T1 领域主线谱系**：本领域主流怎么处理我们关心的问题；有没有和我们同层面（结构/信号/约束）的先例；我们与主流是互补还是竞争。
- **T2 方法组件近邻**：我们每个组件（如 frozen backbone + side branch、routing、fusion）在更广领域（PEFT、MoE、多任务、扩散模型加速……视项目而定）的先例盘点；顺带收结构/方法升级建议。
- **T3 novelty 对抗核实**：把 T0 候选轴 + T1/T2 幸存主张逐条对抗检索裁决（成立 / 部分成立 / 不成立）；产出"能说 / 不能说"红线与必引划界清单；把该文献线的成熟指标平移过来升级我们的评估协议（往往能顺手变成一个协议贡献）。
- **T4 投稿策略**：目标会议确切日期（必须官方来源）、该会口味与 framing 候选（附已录用参照）、证据标准与缺口分级（必须补/建议补/可不补）、Plan B 时间表、竞品状态核实。

每份任务书按 `task_brief_template.md` 写。

## 4. 质量机制（这套流程可信的原因，一条都不要省）

1. **对抗检索纪律**："没有先例"类结论必须附上检索词组合与覆盖范围，不许直接断言空白。
2. **novelty 三分法**：已有工作已做过 / 类似但不完全一样 / 可能空白——禁止夸大。
3. **实时检索**：近两年论文必须联网检索，不许凭模型记忆（模型知识过期且会幻觉）。
4. **待核实标注**：太新而无法二次核实的条目必须标"待核实"；**载重条目**（支撑关键判词的那几篇）在使用前必须点开原文确认。
5. **跨报告回填**：后续任务发现前序报告的错误，写**带日期的更正注记**回填原报告，不悄悄改正文。（rdbp 实例：T3 复核出 T2 引用的 PHATGOOSE −10.2 基线不可比，对外口径当天更换成更干净的证据——对抗复核有真实回报。）
6. **验收动作**（规划 agent 对每份报告必做，checklist 见 task_brief_template.md B 节）：结构合规 → 覆盖检查 → 关键引用抽查 → 与前序一致性 → 整合沉淀。

## 5. Phase 2：整合沉淀

- `research/README.md` 每任务一条状态行：✅ 日期 + 关键裁决一句话。
- 全部交付后写 **`summary_for_<里程碑>.md` 一页**（给汇报/写作 agent 的唯一底稿）：一句话定位、novelty 红线（能说/不能说）、文献格局每任务一句话、划界与竞品清单、实验证据现状（含 pending 的诚实呈现）、下一阶段实验骨架、待核实清单、事实来源指针。

## 6. Phase 3：实验联动

- 每份调研报告的"对后续实验建议"由规划 agent 逐条裁决采纳/不采纳，**采纳项写进实验计划并注明来源任务号**。
- 设计**决策点**：某个关键实验结果决定走叙事 A 还是改造路线 B——两个分支都预先想成"可讲的故事"，实验永远不白跑。
- 评估协议尽量借文献成熟指标平移（rdbp 实例：把模型升级文献的 negative flip rate 平移到人脸 verification，因该域无标准化定义，反而成为低风险的协议贡献）。

## 7. 效率机制（内容 agent 的 token 要花在检索上）

- 启动 prompt **内联全部背景**（方法描述、实验结论），本地只读 2–3 个指定文件，并明说"其余不要读"。
- 项目若有 CLAUDE.md（工程 agent 角色设定），任务书开头**显式声明覆盖**，防止内容 agent 顺着它去干工程的事。
- 范围上限写死：清单表 10–20 篇、精读 3–5 篇；可并行的检索并行。
- 统一交付六段式（Executive Summary / 清单表 / 精读卡 / Gap 分析 / 汇报可用表达 / 实验或写作建议）+ 对话内 ≤10 行执行总结——用户只需转发这 10 行。
- 引用死文件/死路径是零容忍项：任务书里的每个文件引用发出前核实存在。

## 8. 常见坑（rdbp 实战记录）

- 任务书里让 agent"先读 3 个大文档建立上下文"——错，应内联结论、只读方法底本。5 万字的文档阅读会吃掉一半检索预算。
- 用工程语言描述方法去搜文献——搜不到真正的近邻；必须先翻译成论文语言（T0 第 1 步）。
- 拿到"无先例"就兴奋——先看检索词覆盖；三轮下来 rdbp 的 6 条初始主张 5 条被降级收窄，最后活下来的窄带才是真 novelty。
- 竞品情报会过期（venue 转投、录用状态），投稿前设复核点。
